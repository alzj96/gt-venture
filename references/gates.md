# 四道闸：任何行业、任何事都先过这四道

**什么时候读这份**：六问（或副业四问）答完、要查闸门的时候。轻量筛查查主体资格时，只读「一、人：先查主体资格」那一节。

**这个文件解决一个真问题**：规则库覆盖的行业永远有限，中国有几百个行业，而每一条都要人工核一手源。但**要过的闸只有四类，这四类不挑行业**。

所以正确的分工是：**闸门的种类由框架保证（永远完整），闸门里的内容由规则库提供（永远不完整）**。规则库没覆盖的那一格，我们照样能告诉用户"你要过这道闸、大概要什么、去哪儿查"——**那比"我不知道"有用得多**。

---

## 四道闸

| 闸 | 问的是 | 答错的代价 |
| --- | --- | --- |
| **一、人** | **这个人**能不能做这件事 | 主体不合格时，证办得再全也没用 |
| **二、事** | **这件事本身**要不要许可 | 无证经营，罚款到停业 |
| **三、地** | 在**哪个渠道**上线，那个渠道要什么 | 审核不过，或者上线后被下架 |
| **四、钱** | **钱怎么收**、要不要办执照、票怎么开 | 无照经营、税务风险、收不到钱 |

**顺序不能反。** 人不合格 → 后面三道都白查；事没许可 → 渠道审核必然卡；渠道定了才知道要什么材料；钱这一格的答案取决于前三格（个人还是公司、有没有许可）。

另有一组按触发查：预付式消费（**不挑行业**，见下）。

---

## 资质结论是重大主张

**一条资质要求只有在规则库里有逐字原文时才能说出口。** 规则库里没有的，就是不知道。

这条对应的失败是真实的：说错"需要办"，用户白跑一趟；说错"不需要办"，用户可能已经上线了才发现违规。两种错的代价差着量级，所以**绝不给"不需要办证"这类否定结论**。

说不知道的正确形态不是一句"我不清楚"，而是 **指出类目名 + 给查询链接 + 说明这是用户自己几小时能查完的事**。规则文件末尾有完整示例。这比"建议咨询专业人士"有用得多。

引用规则时**必须带拉取日期和来源链接**。超过 90 天的条目，明说"这条最后核对于 X 日期，可能已变更"。官方文档自己就写着"以提交时所要求的材料为准，本文档仅供参考"，把这句转达给用户。

**落到具体。** 不是"你可能需要一些资质"，而是：

> 你描述的是在线课程，按微信的类目表落在「教育服务-教育平台」。那个类目要《增值电信业务经营许可证》，而且核准项目得包含"在线数据处理与交易处理业务"。这个证个人主体办不了，得有公司，还有注册资本和人员社保的要求，具体门槛去问当地通信管理局。（微信开放文档，2026-09-15 核对）

## 按顺序一道一道过

### 先看会不会触发预付式消费

用户的业务里只要出现**充值、储值、会员卡、次卡、年卡/月卡、存杯、买十送一、押金、预售**，或者任何**先收钱、之后分次兑付**的形态，就读 [预付式消费](knowledge/规则-预付式消费.md)。

**这一组和其余两组有个重要差别：用户往往已经在违规状态里**，不是"将来要办什么证"。2024 年 7 月 1 日起，收预付款必须与消费者订立书面合同，而绝大多数小店老板不知道这件事。

所以说法也不一样——不是"你需要准备什么"，是"**你现在这件事得补上，而且今晚就能补**"。

**别用罚款金额开场。** 那个文件里写了为什么：吓住一个开店的人，他会关掉对话，不会去补合同。

### 一、人：先查主体资格

读 [主体资格红线](knowledge/规则-主体资格.md)。

用户提到自己或合伙人是**在编教师、公务员、事业单位人员、医生、律师、公职人员**，或者说了"我老婆/老公/朋友在体制内"，**立刻查这一组，不要等到六问答完**。

**用户是在校学生**也查这一组（E6），但方向相反——**政策是支持的**，要给的是"去问你们学校两件事"（休学规定、知识产权归属），不是"你可能不能创业"。

这一组比类目资质致命得多：类目资质是"要补什么材料"，主体资格是"这个人能不能做这件事"。主体不合格时，证办得再全也没用。

而且它有个反直觉的特点，规则文件开头讲了：**用户往往把那个不合格的身份当成自己最大的优势在讲**。只查类目会给出一个引用规范、来源清晰、却完全答偏的结论——那比说不知道更危险。

**红线判定说多长、什么时候说完回到六问**（实测中这是最大的歧义，用户的两个变通把第 1 问往后推了三轮）：

- **第一次说，只说三句**：踩了哪一条、原文是什么、代价不对称在哪。不要一次把所有推论倒完。
- **用户提变通时，一次只挡一个**，挡完立刻加一句"这个我们待会儿回到报告里细说，先把项目本身问清楚"，然后回到六问。
- **最多挡两轮。** 用户第三次找变通时不要继续辩，说："这条我说清楚了，你回头自己找教育局确认。现在先回到项目本身——" 然后直接问下一问。合规不是这一步的产出，报告才是。
- **真正的展开放在报告的「中国闸门」一节**，那里有空间写全，而且用户能转发给合伙人看。

理由：红线判定是重要的，但它不是诊断。在问问题的阶段陷进合规辩论，用户会带着"这事不能做"的情绪回答后面四问，那四个答案就废了。

### 三、地：再查类目资质

根据用户描述的业务，判断它落在哪些服务类目上，读 [类目与资质](knowledge/平台-微信小程序.md)。

先看规则新不新：

```bash
python3 <技能目录>/scripts/check_rules.py
```

（`check_rules.py` 只读技能自己的规则库，不碰用户数据，所以不接 `--workspace`。）

#### 歧义时停下来

业务落在哪个类目不清楚时，**停下来问，不要猜**。一句话说清楚歧义在哪，用 `AskUserQuestion` 给 2-3 个可能的类目，**每个类目对应的门槛写进问题正文**（选项说明在 WorkBuddy 上不显示），标题只写类目名，让用户选。这是事实题——**不标推荐**，标了他会挑门槛低的那个点。

猜错类目的后果是后面整段闸门分析全是错的，而且错得很有说服力。

### 二、事 和 四、钱

**这两道规则库覆盖得最少，但它们最不挑行业——所以最不能跳过。**

**第二道闸：事（这件事本身要不要许可）。** 规则库**整格空白**：食品经营、医疗器械、人力资源服务、旅行社、出版物、危化品、烟草……一条都没有。

这一格的正确动作**不是猜**，是下面「没覆盖的那一格，标准动作是三句话」：**说出他的业务落在哪一类经营活动上 → 给查询入口（当地市场监管部门 / 12315 / 12345）→ 说明这是他几小时能查完的事。**

**第四道闸：钱（要不要办执照、票怎么开）。** 读 [钱这一格](knowledge/钱-执照收款税票.md)。市场主体登记有一手源；**"有没有不用办执照的口子"的原文在 [电子商务经营者登记](knowledge/规则-电子商务经营者登记.md) D1——「10 万元」那条三句一起给，不要说"你这个规模不用办"**。个人接单的税在主体资格那组的 E9，顺手一起过。

**这两格的错是不对称的**（见上文「资质结论是重大主张」）：说错"需要办"，用户白跑一趟；说错"**不需要办**"，用户可能已经上线了才发现违规。所以这两格**永远不给否定结论**。

## 我们覆盖到哪，逐格摆出来

**这一节要照实说。** 用户凭它决定哪几格自己去查，说满了他就不查了。

### 一、人 —— 覆盖得最厚

[主体资格红线](knowledge/规则-主体资格.md)：在编教师、公务员、事业单位人员、在校学生、在职做副业（竞业与在职条款）、职务成果归属、个人接单的税。

**没覆盖**：医生、律师、会计师、军人、国企任职人员、外籍人士、失信被执行人。这些同样有身份限制，**我们没有一手源，遇到时说不知道**。

### 二、事 —— 几乎空白，这是最大的缺口

**规则库里没有「经营许可」这一组。** 食品经营、医疗器械经营、人力资源服务、旅行社、出版物、危化品、烟草、成品油……全都没有。

这一格的正确动作**不是猜**，是：

> 说出**业务落在哪一类经营活动**上 → 指向查询入口 → 明说这是他几小时能查完的事

查询入口：**当地市场监管部门（12315 / 12345）**、国务院客户端「行政许可」、各行业主管部门官网。

**这一格最容易出事**，因为它的错是不对称的（见上文「资质结论是重大主张」）：说错"需要办"，用户白跑一趟；说错"**不需要办**"，用户可能已经上线了才发现违规。**所以永远不给"不需要办"这种否定结论。**

### 三、地 —— 只覆盖微信小程序一个渠道

[类目与资质](knowledge/平台-微信小程序.md) 覆盖的是**微信小程序**，而且是 200 多个类目里独立开发者高频的几类。

**完全没覆盖**：抖音／快手小程序与小店、支付宝小程序、App Store 与安卓各商店、H5 与网站（ICP 备案和经营许可证的法规原文见 [I 门类卡](knowledge/门类-I-信息传输软件和信息技术服务业.md) I-R2）、公众号、视频号、线下门店（那是"事"和"地"的混合）。

**第三轮差分实测撞到过**：用户做抖音电商，规则库的类目表一条都对不上。**遇到非微信渠道，直接说这一格没覆盖**，别拿微信的类目去套——**平台规则之间不通用**。

### 四、钱 —— 覆盖一半

[要不要办执照、票怎么开](knowledge/钱-执照收款税票.md)：市场主体登记（已核一手源）、豁免的那条线（原文在电子商务经营者登记 D1、D5）。
个人接单的税在 [主体资格红线](knowledge/规则-主体资格.md) E9。
收预付款的另有一组：[预付式消费](knowledge/规则-预付式消费.md)，**不挑行业，触发就查**。

**没覆盖**：发票的具体开法、对公账户、社保、跨境收款。

## 没覆盖的那一格，标准动作是三句话

**不是"我不知道"，是这三句**：

1. **你这件事落在哪一类** —— 说出类别名（「你这是餐饮服务」「这属于人力资源服务」），类别名是他去查的钥匙
2. **去哪儿查** —— 给具体入口，不是"咨询专业人士"
3. **这是你几小时能查完的事** —— 降低他的畏难感，也说清楚这件事得他自己做

> 你这个要办的是食品经营许可，**这一类我的规则库没覆盖，具体要什么材料我不知道**。去问当地市场监管部门，或者打 12345，一般能当场问清楚。这是你一个下午能办完的事，**但一定要在开张之前办**。

**三句都给，比给一条编出来的资质要求强一百倍。** 编一条听起来合理的资质要求，是这个技能定义里最严重的失败。

## 把闸门结果存进档案

四道闸走完（**包括没覆盖的那两格**），写一段闸门检查结果存进去：

```bash
python3 <技能目录>/scripts/archive.py --workspace "$(pwd)" gate --project "<项目名>" --file <闸门结果临时路径>
```

内容至少包含：**四道闸逐格的结论**（人 / 事 / 地 / 钱），每格写查了没有、结论是什么；有原文的附原文、拉取日期、来源链接；**没覆盖的那几格写明业务落在哪一类、让用户去哪儿查**；触发了预付式消费的单列一条。

**这一步不能跳。** 用户下次回来时，闸门结论比六问答案更容易忘——他会记得自己说过什么，但记不住"教育类目要哪个证"。

## 为什么规则库不追求"全"

第一轮差分测试的结论，原样放在这里：

> 规则库的边际价值**只存在于它覆盖的范围内**，范围之外我们没有内容优势。推论很实际：规则库不该追求"全"，该追求"**深**"和"**新**"——覆盖到的地方要给逐字原文、日期、来源，那是模型给不了的；覆盖不到的地方老实说不知道。

**"广"这一维交给这四道闸，不交给内容。** 内容可以永远不全，框架必须永远完整——**用户拿到的那份「你要过哪四道闸」，不挑行业**。
