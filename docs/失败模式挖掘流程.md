# 失败模式怎么持续挖进来

失败模式库现在 14 条：5 条产自我们自己的两次诊断，3 条挖自社区团购，3 条挖自 AI 坟场，3 条挖自知识付费与本地生活。要长成知识库，得有稳定的原料来源和一套不会越挖越水的流程。

这是**工坊侧**的活，和规则库同理：抓取、提炼、人工确认、发版。**不在用户会话里做**——理由和规则库的「构建期刷新」一条相同（抓取在工坊完成、人工过目后发版，运行时只读带日期戳的静态内容），一样适用。

## 一、原料按可用性排序

| 来源 | 量级 | 语境 | 用法 |
| --- | --- | --- | --- |
| **我们自己的诊断** | 每次 1-2 条 | 中国，一手 | **最高优先**。已产出 5 条，每条都带真实上下文 |
| **用户回流的驳回/失败经历** | 待建 | 中国，一手 | 见 [复利回路移植方案](复利回路移植方案.md)。**模型不可能知道的那部分** |
| **IT桔子 死亡公司数据库** | 近十年 3.24 万家 | 中国 | 挖机制的主力。注意它的死因标签（伪需求/商业模式匮乏/竞争激烈）太粗，要往下钻 |
| **CB Insights** | 483 份复盘 | 美国 | 机制可迁移，语境不可迁移 |
| **Autopsy.io** | 2000+ 份 | 全球 | 同上，量最大 |
| **AI 坟场类**（404Tomb 597 条 / The AI Cemetery 115 份带解剖 / killedbyai 111 条 / Tool Directory 285 条） | 合计上千 | 全球，AI 品类 | 量大但**标签质量最差**，见下文陷阱 |

**IT桔子 抓不动**：`itjuzi.com` 返回 HTTP 412 + 随机 token，是瑞数那类 JS 挑战。别硬试。它的数据要靠公开报道转述（每经网、界面、21经济网这些对具体数字的转述相当完整）。

**一个数值得记住**：IT桔子的数据里 **83% 死在种子轮和 A 轮之前**。我们诊断的正是那个阶段——这既说明这件事值得做，也说明**我们面对的失败模式主要是早期的**（需求、渠道、形态），不是后期的（组织、扩张、融资）。挖的时候优先挖早期模式。

## 二、挖掘流程（每次一批，别贪多）

### 1. 选一个主题，不是选一批公司

按**死因**或**行业**切一刀，比如「社区团购死了哪些、怎么死的」「知识付费的早期死法」。一次一个主题，5-10 份复盘。

按公司挖会得到一堆互不相关的故事；按主题挖才能看出重复出现的那个动作。

### 1.5 先看一眼这个库的"死因"栏可不可信

**AI 坟场是最好的反面教材。** Tool Directory 的统计说：

> 最常见死因是**域名过期——占全部条目 40%，占真死（非被收购）的 64%**。

**"域名过期"不是死因，是死亡的观测信号。** 它是爬虫判断"这个产品没了"的方法，被当成了"这个产品为什么没了"的答案。

按这条做诊断会得出「记得续费域名」。

**判据**：看到一个死因标签，问一句「**这是它做错的事，还是我们发现它死了的方式？**」分不清的整栏都不能用。

同类可疑标签：`资金耗尽`（症状）、`团队解散`（结果）、`被收购`（不一定是失败）、`没有 PMF`（同义反复）。

### 2. 问动作，不问品类

对每份复盘问的是：**这些项目具体做错了什么动作？**

不是「它属于什么品类」，不是「创始人说它为什么死」。

> **创始人自述的死因不可信。** "钱烧完了"是症状不是原因，"没找到 PMF"是同义反复。要挖的是那之前发生了什么——他在哪一步做了什么决定，导致后来钱烧完了。

### 3. 写成诊断测试，不是写成教训

这一步决定了这条机制有没有用。

**没用的写法**：「要重视需求验证」——正确、无法执行、无法判断自己中没中。

**有用的写法**：「第 1 问的答案里，付出的人和要付钱的人是不是同一批？」——能从六问答案直接答出来，答不出来就是没命中。

**判据：这条测试能不能用六问已有的答案回答？** 不能就重写，或者说明它需要补问哪一句。

### 4. 找反例（这一步不许跳）

**谁有这个病却活下来了，靠什么活的？**

- 找得到 → 反例本身就是出路。写进去。
- 找不到 → 标 `待证`，**不入库**。

这一步是基数谬误的解药。失败案例库只收录失败者，不强制找反例的话，挖出来的每条机制都会长成"这样做会死"——而真相往往是"这样做很难，但有人做成了，靠的是 X"。

后者对用户有用，前者只会让他瘫痪。

### 5. 人工过目后入库

和规则库一样：AI 提炼成候选，人确认后才写进文件。**永不自主入库**。

理由同 gstack 的 dream cycle（`gstack-distill-free-text` 的 `Codex #15 trust boundary`）：诊断结论出错的代价由用户承担，这个代价不能交给自动化。

## 三、入库检查清单

每条新机制入库前逐项核：

- [ ] 有**诊断测试**，且能从六问答案直接回答
- [ ] 有**为什么致死的机制**，不是标签（"竞争激烈"不算机制，"定价地板被免费产品按死"才算）
- [ ] 有**反例**，说得出谁靠什么活下来了
- [ ] 有**出路**，且出路不是"别做"
- [ ] 标了**来源**，自产的写自产，挖来的给链接
- [ ] 没有整段搬运他人复盘正文（只存我们写的机制 + 引用链接）
- [ ] 和已有的条目**不重复**——重复的合并，别堆数量

## 四、什么时候该停

**库不是越大越好。** 一次诊断只会用上 1-2 条，命中三条以上时我们自己的规矩是只讲最致命的那条。

**14 条时就已经撞上上下文预算了**（全文 9876 字符 ≈ 4900 token，是所有 reference 里最大的一个）。当时的处理是**加索引改成按需读**：文件开头两张表（按六问定位 / 按业务形态定位），模型只读索引 788 token + 命中的 1-3 条，比全读省约 70%。

有测试钉着两件事：**新条目必须同步进索引**（漏进索引的条目等于不存在，模型永远读不到，比写错更隐蔽），以及**索引本身不能长成第二个全文**（超过全文 45% 就该分组）。

再往上堆的话，下一步是**拆成多个文件按形态分**（AI 类 / 内容类 / 平台类 / 线下类），不是继续加索引行。

粗略的停止线还是 20-30 条。

## 五、和规则库的分工

| | 规则库 | 失败模式库 |
| --- | --- | --- |
| 存什么 | 官方**怎么规定** | 项目**怎么死的** |
| 来源 | 一手源原文 + 日期 | 复盘提炼 + 我们的诊断 |
| 错的代价 | 用户违规上线 | 用户被误导或被吓退 |
| 语气 | 逐字引用，不改写 | 必须改写成诊断测试 |

**规则库要准，失败模式库要能用。** 前者错了是事故，后者错了是噪音——但噪音积累到一定程度，用户就不信任何一条了。
