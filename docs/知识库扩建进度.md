## A1 规划：SKILL.md 每一节去哪

### 先定三条原则

1. **参考文件读进来，也会一直留在对话里。** 瘦身省的是「每一轮都背着的字」，如果把 SKILL.md 平均拆成几份、每次诊断照样全读，一个字都没省。所以**按「什么时候才需要」拆，不按主题平均拆**：
   - 每次诊断都要读的（开场、六问、四道闸、报告）——压紧，不放只在少数情况用得上的东西
   - 触发了才读的（接着上次、轻量筛查、他不方便答、要跳过流程、体制内、预付、AI）——单独成文件，没触发就永远不进对话
2. **常驻的只放两种东西**：一是**在读到任何参考文件之前就可能被违反的**（第一句回复就要弹选项、第一条命令就要分清两个目录、用户开口就问「要办什么证」）；二是**每一轮都在用的**（铁律、让他纠正、默认是选项）。其余的在核心里只留一句 + 链接。
3. **挪位置，不删行为。** 下沉时原句照搬，不顺手改写；参考文件里已经有的同一段话，逐句对过再删 SKILL.md 那份，**对不上的那句补进参考文件**。

## A6 测速：瘦身前的基线，和瘦身后怎么测

**要回答的问题**：SKILL.md 常驻 3 万字，是不是 WorkBuddy + 免费 Hy4 一问要一分多钟的原因之一？A 把它压到了 3,644 字，但这件事**还没测**。

### 计时脚本

在仓库外的内部文档目录 `tools/wb_timing.py`（不进仓库：它要读 WorkBuddy 日志，**日志里有本地 MCP 的 Bearer token**，脚本只输出从时间戳和工具名算出来的数字，从不打印日志原文）。

算法：**一问的模型耗时 = 点完上一个选项框 → 下一个选项框弹出来**。WorkBuddy 界面上「已处理 N 分钟」那个计时器把等用户点选的时间也算进去了，不能用。另外单独报每次模型请求的时长，以及其中的**首字延迟**（请求发出 → 开始流式返回）——模型得先把整个上下文读一遍才吐第一个字，**常驻上下文变短，最该变的是这个数**。

### 瘦身前的基线（2026-09-16 小周那场，Hy4 preview 免费档）

| 量 | 数 |
| --- | --- |
| 一问的模型耗时（14 问） | **中位 66.7 秒**，平均 76.8 秒，最短 28.6，最长 194.0 |
| 同上，不含联网那一问（13 问） | 中位 63.3 秒，平均 69.5 秒 |

最慢的两问：闸门检查那一问 194 秒（7 次 Read + 1 次 Write + 7 次模型请求），查竞品那一问 172 秒（2 次联网）。**普通一问多数是 2 次模型请求 + 1 次存档，一分钟上下**——所以一问慢的主要是那两次请求本身，每次十几秒，不是工具调用多。
