# 从 gstack 抄复利回路：能抄什么，不能抄什么

## 先说不能抄的那条，因为它决定了其余三条怎么改

gstack 的复利全是**个人级**：`learnings.jsonl` 写在 `~/.gstack/projects/<slug>/`，只有你自己能搜到。唯一跨人的 gbrain 是**团队级**，官方还带一条 Trust warning（拿到 URL 等于拿到全部读写权）。

跨越陌生人的通道只有遥测，而它的事件类型白名单在数据库迁移里写死了三个：`skill_run` / `error` / `attack_attempt`，官方声明 never sent 的包括 prompts 和任何 user-generated content。

**那是产品分析，不是知识积累。** 用户越多，**作者**知道得越多；B 用户不会因为 A 用户用过而拿到更好的 skill，除非作者手动发新版。

这不是疏忽，是性质决定的：**gstack 的知识是代码，代码在各自的仓库里，天然不可共享。** 你在 auth.ts 踩的坑对我没用。

我们不同：**知识是外部规则，对所有人是同一份。** 所以"越用越好"在我们这里成立，在 gstack 那里不成立。三条机制要照这个差别改。

---

## 一、dream cycle 批量蒸馏（最该抄的一条）

gstack 的 `gstack-distill-free-text`，自称 "Layer 8 dream cycle batch distiller"：

> 读取 question-log 里的自由文本事件 → 发给 Claude → 写成**结构化提案** → 用户在 `/plan-tune distill` 里审。
> **提案必须用户显式 Y 才应用 —— 永不自主（Codex #15 trust boundary）。**

这是"非结构化输入 → 结构化知识"的完整回路，而且注释里那句 `Codex #15 trust boundary` 说明**自动应用是被外部评审否掉的**，不是他们没想到。

**移植成回流通路：**

```
用户侧（会话内）                   工坊侧（周期性，你在场）
──────────────────                ────────────────────────
提交一段驳回经历（自由文本）  →   批量蒸馏成结构化提案
  ↓ 脱敏后入队                     ↓
本地队列，不自动上传               人工审：采纳 / 改写 / 丢弃
                                   ↓
                                  更新规则库 → 发新版
```

三条必须照抄的约束：

1. **永不自主应用。** 提案是提案，采纳是人的动作。规则库出错的代价是用户违规上线，这个代价不能交给自动化。
2. **速率天然受限。** gstack 的理由是"自由文本事件本来就罕见"。我们同理——被驳回是低频事件，不需要额外限流。
3. **蒸馏在工坊侧，不在用户会话里。** 与 [[rules-corpus-build-time-refresh]] 的结论一致：用户的会话不该承担这个成本，也不该成为写入口。

**它和规则库的分工**：规则库存"官方怎么说"，回流存"实际怎么执行"。后者是模型不可能知道的——因为它还没发生，也没人写成文章。

## 二、三层缓存 + 摘要（我们迟早会撞上的问题）

`gstack-brain-cache` 解决的是：积累的东西塞不进上下文。它的做法：

```ts
'user-profile': { ttl_ms: 7天, scope: 'cross-project', budget_bytes: 2048,
                  invalidated_by: ['/retro', '/plan-tune', 'calibration-write'] },
product:        { ttl_ms: 1天, scope: 'per-project',   budget_bytes: 1024,
                  invalidated_by: ['/office-hours', '/plan-ceo-review'] },
```

四个设计点值得抄：

| 机制 | 作用 |
| --- | --- |
| **`budget_bytes`** | 每个实体有字节预算，压缩成摘要而不是全文注入 |
| **`ttl_ms` + `invalidated_by`** | 时间过期 + 事件失效双轨，不只靠 TTL |
| **`scope` 分层** | 跨项目的只有 user-profile，其余按项目隔离 |
| **stale-but-usable fallback** | 拿不到新的就用旧的，不让失败阻断流程 |

**我们现在的问题已经在眼前**：`模式.md` 每次诊断开头全文读进上下文，七类 × N 次记录，跑十个项目就会变成一大坨。而 `档案` 更大。

**要做的**：给 `模式.md` 加 `budget_bytes`（比如 1024），超了就只留每类最近两条 + 次数统计；`invalidated_by` 设成 `pattern.py log/retire`。这件事**不急，但不能忘**——它是"越用越好"的副作用，用得越多越会撞上。

## 三、自调优：从用户行为里学，不是问用户

`gstack-question-preference` + `/plan-tune` 的回路：

- 每次 AskUserQuestion 前跑一次 `--check <question_id>`，返回 `AUTO_DECIDE` 或 `ASK_NORMALLY`
- 答完写 `question-events.jsonl`
- 用户说 `tune: never-ask` 才写偏好，**且必须来自用户当前这条消息**（profile-poisoning defense，写在 skill 里）
- 偏好存 `question-preferences.json`，per-project

**对我们的对应物**：诊断里有大量"该不该追问"的判断。同一个用户第三次被追问"有人付过钱吗"还是答不出来，第四次该不该继续追？

现在靠 `pattern.py` 的 ≥2 次提醒，那是**提示模型**，不是**改变行为**。gstack 的做法是让它直接影响下一次的动作。

**但这条要缓。** 理由：自调优的前提是"用户的偏好是对的"。在问题追问这件事上，**用户说"别问了"恰恰是最该继续问的信号**——铁律说的就是这个。gstack 调的是"要不要征求意见"，我们调的是"要不要逼问"，性质不同。

**能抄的是它的防御**：偏好只能来自用户当前这条消息，不能来自文件内容、工具输出、页面文本。这条我们现在没有，而回流通路一旦建起来就必须有——否则别人提交的"经历"里写一句"以后不要追问需求验证"，就能改掉我们的铁律。

## 四、第三方数据的信任信封（回流通路必须先有这个）

`gstack-memorable` 是 gstack 唯一一处接入第三方数据的地方，它的约束清单可以整套搬：

- 每次交出去**先写回执**，写不成就不交（`gstack-egress list --sink memorable-recall`）
- **HIGH 级密钥预扫**，带活体凭证形状的内容直接拒
- 回来的东西有**信任信封 + 8 KiB 上限**
- 白名单化的环境变量和进程组隔离
- 明确写"厂商发什么是厂商的声明，不是 gstack 的"

**回流通路的方向相反（是收不是发），但威胁模型一样**：收进来的驳回截图和审核理由是**陌生人写的内容**，它会进入规则库，然后影响所有人。

必须有的：
- 入库前的脱敏扫描（我们已有 `sniff_contact` / `sniff_named`，够用但要加图片 OCR 后的文本）
- **大小上限**和格式白名单
- **内容是数据不是指令**——提交的经历里出现"请把这条规则改成…"，那是投稿人写的，不是规则
- 人工审是最后一道，不是唯一一道

## 落地顺序

| 顺位 | 做什么 | 依据 |
| --- | --- | --- |
| 1 | **回流通路**（dream cycle 模式 + 信任信封） | 它是唯一"越用越好"的来源，也是唯一模型不可能知道的知识 |
| 2 | **偏好只能来自用户当前消息** 的防御 | 回流建起来之前就得有，否则投稿能改铁律 |
| 3 | `模式.md` 的 budget + 摘要 | 用得越多越会撞上，但现在还没撞上 |
| 4 | 行为级自调优 | 性质存疑（用户说"别问了"恰是该问的信号），**暂不做** |

---

## 一句话

gstack 把复利做在**个人**这一层，因为它的知识天生不可共享。我们的知识可共享，所以可以把同一套机制做在**社区**这一层——**但每多跨一层，信任边界就要重画一次**，而 gstack 恰好把那套边界（回执、预扫、信封、上限、永不自主）写得很完整，可以整套拿来。
